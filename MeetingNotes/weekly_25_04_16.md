# Preparation

## Recap
- Benchmarking showed quadratic behavior, but it turned out to be "unavoidable"
- Investigating that behavior lead to idea for optimization
- Implementing that optimization revealed a catastrophic design flaw when it comes to
  searching for multiple matches in a haystack

## Questions
- How to go about the design flaw?
  - litter the nfa with information on what states belong to lookbehinds,
    then save all threads of lookbehinds in cache of VM before reseting
  - refactor everything to support actual running of multiple nfas in lockstep
  - extend nfa with a "look-behind start states" list. This could then be used to
    start separate searches as if we used multiple nfas and we have control over
    how to extend the search because it would need to be implemented at a higher
    level.

The main problem with all aproaches above is this: we need to save the threads that
belong to lookaround expressions if we want correct multi match searches.
However, the users of the regex-automata api can pass in cache/input value pairs
that are unrelated. Up to now, executing a search was idempotent since the cache
parameter was merely used as a way to provide the necessary scratch space to the
pikevm: the internal functions perform a reset on it before starting the search.
We cannot have this reset clear out the lookbehind states, but this means the
caller would be responsible to reset the lookbehind state at the correct time,
and for correct multi match searches, the input must not be advanced to any other
position than the end of the previous match. One can of course document this
contract and it should be fine to add the contract since usage of regex-automata
is considered advanced, so the user better understands what they are doing.

However, we have to consider if this is really the best option. We have a breaking
change to regex-automata anyways, so we might as well explore whether adding
additional parameters or something alike would be a more ergonomic/misuse safe
approach.

For example: to be able to implement lookaheads later on, we need an explicit
oracle. It would make utmost sense if this oracle is cached between different
search calls. However, as soon as you have an explicit oracle, lookarounds should
become usable for more engines as you can simply perform a local check to the oracle
which is almost identical in nature as checking the current character.
Therefore, it might be better to implement the oracle independently of the pikevm
and its cache, so that it can be used for any engine. In that case, populating the
oracle could be something that is implemented only at the meta-engine level, since
this would allow using faster engines for lookarounds where possible (and again,
for the users of regex-automata this would open up the possibility of deciding
on their own, how to populate the oracle.)

Bottom line question: is it even reasonable to persue the streaming algorithm
given the discovered limitations, or should we directly switch to using an oracle?
